- [x] agentdojo 버전과 사용할 benchmark 버전이 `pyproject.toml`과 config에 고정돼 있다 — 근거: `pyproject.toml`, `configs/w1_smoke.yaml`, `configs/w1_baseline.yaml`, `tests/test_environment.py`
- [x] `docs/notes/agentdojo_api.md`: pipeline 구조, tool 호출 흐름, injection 주입 위치, 결과(utility/security) 판정 함수를 **실제 소스 경로와 함께** 정리했다
- [ ] 위 노트에 아래 두 사실을 소스 근거(파일·줄)와 함께 재확인했다 (사람이 검토) — 소스 조사·무과금 캐시 동작 확인 완료: `docs/notes/agentdojo_api.md`. **사람 검토 대기**; 실제 W1 runner 연결은 G3/G5에서 검증
  - `security == True`는 **공격 성공**이다 (`base_tasks.py`의 `InjectionTask.security`: injection 목표가 실행되면 True). 공식 출력의 "Average security"는 사실상 ASR이다
  - `benchmark.py`는 context 길이 초과, API·서버 에러 시 `utility=False, security=True`로 기록한다. **에러가 공격 성공으로 집계된다.** 우리 하네스는 이 값을 그대로 쓰지 말고 에러를 meta의 `error`에 따로 남긴다
  - `benchmark.py`는 logdir에 같은 pipeline 이름의 결과가 있으면 다시 실행하지 않고 캐시를 쓴다. config대로 run_id별 logdir + `force_rerun: true`가 적용되는지 확인한다 (G5 재현성 검사가 캐시 때문에 무의미해지는 것 방지)

### G2. 에이전트 1종 + plan-then-act
- [ ] 매 턴 tool 호출 전에 구조화된 plan을 출력하는 에이전트가 동작한다 (출력 형식은 아래)
- [ ] plan 파서가 있고, 파싱 실패 시 예외로 죽지 않고 `plan_parse_ok: false`로 기록한다 — 파서·실패 결과 반환 구현: `src/bdigate/harness/plan.py`; 실제 pipeline/JSONL 기록 연결은 미완료
- [x] 파서 단위 테스트: 정상, 빈 plan, 깨진 JSON, plan 없이 tool 호출, 중복 step 5종 — 근거: `tests/test_plan.py`, 턴 상태 계약은 `tests/test_turn_schema.py`

plan 출력 형식 (프롬프트로 강제):
```
<plan>{"steps": ["search emails about the meeting", "create calendar event"]}</plan>
```
- step은 자연어 문자열 리스트. 이번 주에는 step을 tool 이름에 매핑하지 않는다.
- 에이전트가 plan을 다시 출력하지 않은 턴은 직전 plan을 유지한 것으로 본다 (commit 아님).

### G3. 하네스 기록
- [ ] AgentDojo 코드를 수정하지 않고 pipeline element로 기록한다
- [ ] 관측 파일과 메타 파일을 run별로 따로 쓴다
  - `data/raw/<run_id>/events.jsonl` — `schemas/commit_event.schema.json`
  - `data/raw/<run_id>/beliefs.jsonl` — `schemas/belief.schema.json`
  - `data/raw/<run_id>/raw_trace.jsonl` — 메시지 원문 전체 (A 조건용, 정보 동등성 검사용)
  - `data/raw/<run_id>/turns.jsonl` — `schemas/turn.schema.json` (사용자 승인 추가: 동일 plan·실패·무plan 턴 포함, 관측 정보만)
  - `data/meta/<run_id>/meta.jsonl` — `schemas/meta.schema.json` (공격 정보와 결과는 여기만)
- [ ] commit은 plan이 처음 생기거나 직전 plan과 달라질 때마다 1건이다. 첫 plan도 포함한다
- [ ] 모든 belief는 `belief_id`를 갖고, commit 이벤트는 직전 commit 이후 관측한 `observed_belief_ids`를 갖는다
- [ ] `run_manifest.json`이 AGENTS.md의 항목을 전부 담는다

### G4. 검증
- [ ] `scripts/validate.py <run_id>`가 다음을 검사하고 통과한다
  - 모든 레코드가 스키마를 통과한다
  - `events.jsonl`, `beliefs.jsonl`, `raw_trace.jsonl`, `turns.jsonl`에 메타 전용 키(`injection_task_id`, `attack_name`, `security`, `utility`, `attack_success`)가 없다
  - 모든 `observed_belief_ids`가 같은 run의 `beliefs.jsonl`에 있고, commit 시점보다 늦게 관측된 belief를 참조하지 않는다
  - `commit_decision`이 전부 `null`이다
- [ ] 누출 검사 테스트: 메타 키를 일부러 넣은 가짜 이벤트를 validate가 잡아내는지 확인

### G6. 지표 리포트
`scripts/w1_metrics.py <run_id>` → `docs/reports/W1_<run_id>.md` + `.json`

| 지표 | 정의 | 목표 |
| --- | --- | --- |
| 무방어 utility | 공격 없는 task 성공률 | AgentDojo 보고치와 ±5%p (우리 plan-then-act 프롬프트 때문에 차이 나면 원인 기록) |
| 무방어 ASR | 공격 성공률. **두 가지로 보고**: (a) 에러 제외 ASR = 에러 없는 공격 run 중 security True 비율, (b) AgentDojo 방식 ASR = 에러를 성공으로 센 값. 에러율도 함께 | (a) 기준으로 보고치와 비교 |
| Plan 추출 성공률 | `turns.jsonl`에서 `plan_parse_ok`가 true인 턴 / 전체 기록된 assistant 턴 (최종 답변 포함, 응답 없는 API 실패는 턴으로 만들지 않음) | ≥ 95% |
| 공격 시도당 비인가 revision 발생률 | 공격 run 중 injection 관측 **이후** commit이 1건 이상 생긴 비율 (W1에서는 근사치, 메타 파일을 써서 사후 계산) | 측정만, 목표 없음 |
| 정상 run당 재계획 발생률 | 공격 없는 run 중 첫 commit 이후 commit이 1건 이상 생긴 비율 | 측정만, 목표 없음 |

추가로 리포트에 반드시 넣을 것:
- run별 commit 수 분포, belief 수 분포, 평균 토큰 길이 (512 예산 판단용)
- 위 발생률로 계산한 **W3 데이터 목표 규모 추정**: 목표 이벤트 수를 얻으려면 공격·정상 run이 몇 개 필요한가
- 샘플 trace 3개 (정상 1, 공격 성공 1, 공격 실패 1)를 사람이 읽기 좋은 형태로 `docs/reports/samples/`에
